# IR dumps, one file per level

Generated by [`../dump-examples.sh`](../dump-examples.sh) and checked by the
`dumps` ctest entry, which regenerates them into the build tree and compares. If
a pass changes what the compiler emits, that test fails rather than leaving these
files quietly wrong.

Three programs, each chosen for something it shows:

| Program | Shows |
| --- | --- |
| [`../ex.toy`](../ex.toy) | The running example: a generic function, shape declarations, a call |
| [`../struct.toy`](../struct.toy) | A composite type that disappears before lowering |
| [`../transpose.toy`](../transpose.toy) | `transpose(transpose(x))` folding, on its own |

## Levels

| File | Level |
| --- | --- |
| `<prog>.ast.txt` | The parse tree. `-opt` does not affect it, so it is captured once |
| `<prog>.mlir.txt` | Toy dialect, shapes still unranked where they came from a function |
| `<prog>.mlir-affine.txt` | Affine loops over memrefs, with `toy.print` still standing |
| `<prog>.mlir-llvm.txt` | The LLVM dialect, nothing else left |

Each level except the AST also has a `.opt.txt` (the same level with `-opt`) and a
`.opt.diff` between the two. The diffs are usually the fastest way to see what a
stage of the pipeline actually did:

| Diff | What it shows |
| --- | --- |
| `ex.mlir.opt.diff` | Inlining removes the function, the reshapes fold, shapes resolve from `tensor<*xf64>` to `tensor<3x2xf64>`, and CSE turns two transposes into `toy.mul %1, %1` |
| `struct.mlir.opt.diff` | Five mentions of `!toy.struct` become none. Folding `struct_access` of a `struct_constant` is what lets the rest of the pipeline ignore the type |
| `transpose.mlir.opt.diff` | The function body collapses to `toy.return %arg0`, which is only expressible while the op still means transpose |
| `*.mlir-affine.opt.diff` | Loop fusion merges two loop nests and one buffer allocation disappears |

The levels stop at the LLVM dialect. `-emit=llvm` is past the translation out of
MLIR, so it belongs to LLVM's code generation rather than to this compiler's
abstraction levels; [`../../09-lowering-to-llvm.md`](../../09-lowering-to-llvm.md)
covers it, including what `-O3` does to these programs.

## Regenerating

    docs/examples/dump-examples.sh            # rewrite these files
    docs/examples/dump-examples.sh --check    # what the ctest entry runs
    TOYC=path/to/toyc docs/examples/dump-examples.sh

Nothing in these dumps depends on the working directory or on the absolute path
of the input. MLIR prints locations only when asked, and the debug metadata that
does carry a filename appears after translation, at a level this set does not
capture.

They do depend on the LLVM version, which is 24.0.0 here. The Toy levels are
stable across versions; `mlir-llvm` is the one that moves when LLVM changes how
it spells its own dialect, so a version bump means rerunning the script and
reading the diff before committing it.
