# IR trace: one program, pass by pass

This follows one Toy program through every pass of the affine pipeline, with a
note at each boundary saying what changed and why. The numbered walkthroughs
explain how each component is written; this shows what those components do to
one program, in order.

The trace comes from a committed dump, so every claim here can be checked
against it:

    docs/examples/dumps/codegen.after-each-pass.mlir

produced by `--mlir-print-ir-after-all` and regenerated by
[`examples/dump-examples.sh`](examples/dump-examples.sh), which the `dumps` test
compares against what the compiler currently emits.

If the syntax is unfamiliar, [00. MLIR basics](00-mlir-basics.md) covers how to
read an operation first.

## The program

`reference/tests/Ch2/codegen.toy`, upstream's own running example:

```toy
def multiply_transpose(a, b) {
  return transpose(a) * transpose(b);
}
def main() {
  var a<2, 3> = [[1, 2, 3], [4, 5, 6]];
  var b<2, 3> = [1, 2, 3, 4, 5, 6];
  var c = multiply_transpose(a, b);
  var d = multiply_transpose(b, a);
  print(d);
}
```

Three properties of this program explain most of what the trace does:

- `a` and `b` hold the same six values, one written as a nested literal and one
  reshaped from a flat one.
- Both calls pass the same two shapes, so there is one specialization, not two.
- Only `d` is printed, so the first call's result is dead.

## The pipeline

The pass list, with each pass's options stripped for readability:

```console
$ build/bin/toyc reference/tests/Ch2/codegen.toy -emit=mlir-affine -opt --print-pipeline 2>&1 | tr ',' '\n' | sed 's/{.*//'
builtin.module(inline
toy.func(canonicalize
toy-shape-inference
canonicalize
cse)
toy-to-affine
func.func(canonicalize
cse
affine-loop-fusion
affine-scalrep))
```

`inline` and `toy-to-affine` run on the module, four passes run once per
`toy.func`, and four more run once per `func.func`, which only exists after the
lowering. [11. Driver and pipeline](11-driver-and-pipeline.md) covers why the
anchor matters.

The Toy-level passes are not conditional on `-opt`. Asking for the affine level
runs them either way, because shape inference is a prerequisite for lowering: a
pattern cannot build a loop nest over a tensor whose rank is unknown. What
`-opt` adds at this stage is the last two entries, `affine-loop-fusion` and
`affine-scalrep`. Ask for the Toy level alone and the pipeline is empty:

```console
$ build/bin/toyc reference/tests/Ch2/codegen.toy -emit=mlir --print-pipeline 2>&1
builtin.module()
```

## The trace

The dump records thirteen pass boundaries:

```console
$ grep -c 'IR Dump After' docs/examples/dumps/codegen.after-each-pass.mlir
13
```

The sections below number them 1 to 13 in the order they appear, and every
excerpt is quoted from that file.

### Banners 1 to 4: the inliner, and its own canonicalizer

The first three banners all say `CanonicalizerPass`, and none of them is the
canonicalize pass from the pipeline above. The inliner runs its own
`default-pipeline=canonicalize` on the functions it is working on, which is why
`InlinerPass` reports last at banner 4 even though its effects appear at 3.

Banner 1 is that canonicalizer on the callee. Nothing folds: the body is four
operations over unranked tensors and none of the patterns apply.

Banner 2 is the same pass on `main`, and it is doing real work:

```mlir
toy.func @main() {
  %0 = toy.constant dense<[[1.000000e+00, 2.000000e+00, 3.000000e+00], [4.000000e+00, 5.000000e+00, 6.000000e+00]]> : tensor<2x3xf64>
  %1 = toy.generic_call @multiply_transpose(%0, %0) : (tensor<2x3xf64>, tensor<2x3xf64>) -> tensor<*xf64>
  %2 = toy.generic_call @multiply_transpose(%0, %0) : (tensor<2x3xf64>, tensor<2x3xf64>) -> tensor<*xf64>
  toy.print %2 : tensor<*xf64>
  toy.return
}
```

Two declarations, two reshapes and two constants have become one `%0` used four
times. The reshape patterns folded `b`'s flat literal into its declared shape,
and the folder then found the result identical to `a`'s constant and reused it.
[06. Patterns and folding](06-patterns-and-folding.md) has the rules.

Note `%1`. Its result is unused, and it is still here, because
`toy.generic_call` is not `Pure`: MLIR must assume a call has side effects, so
nothing may delete it.

Banner 3 is the canonicalizer again, after inlining:

```mlir
toy.func @main() {
  %0 = toy.constant dense<[[1.000000e+00, 2.000000e+00, 3.000000e+00], [4.000000e+00, 5.000000e+00, 6.000000e+00]]> : tensor<2x3xf64>
  %1 = toy.cast %0 : tensor<2x3xf64> to tensor<*xf64>
  %2 = toy.cast %0 : tensor<2x3xf64> to tensor<*xf64>
  %3 = toy.transpose(%1 : tensor<*xf64>) to tensor<*xf64>
  %4 = toy.transpose(%2 : tensor<*xf64>) to tensor<*xf64>
  %5 = toy.mul %3, %4 : tensor<*xf64>
  toy.print %5 : tensor<*xf64>
  toy.return
}
```

Both calls are gone and only one body remains. Two things happened here. The
`toy.cast` operations are new: the call passed `tensor<2x3xf64>` into parameters
typed `tensor<*xf64>`, and the inliner asks the dialect to materialize a cast
rather than bridging that itself ([07. Interfaces](07-interfaces.md)). And the
dead call's body was deleted, which the call itself never could be: once
inlined, the body is `transpose` and `mul`, both `Pure`, so the canonicalizer
may remove them.

Banner 4 is the `InlinerPass` dump of the whole module. It matches banner 3 with
`module { ... }` around it, which is the clue that the inliner's own pipeline
had already finished the work.

### Banner 5: a pass with nothing to do

The pipeline's first `canonicalize` on `toy.func` produces output identical to
banner 4. That is informative: the inliner already ran a canonicalizer, and the
casts cannot fold yet because their operand and result types still differ. They
become identities only after the next pass.

### Banner 6: shapes become concrete

```mlir
  %1 = toy.cast %0 : tensor<2x3xf64> to tensor<2x3xf64>
  %2 = toy.cast %0 : tensor<2x3xf64> to tensor<2x3xf64>
  %3 = toy.transpose(%1 : tensor<2x3xf64>) to tensor<3x2xf64>
  %4 = toy.transpose(%2 : tensor<2x3xf64>) to tensor<3x2xf64>
  %5 = toy.mul %3, %4 : tensor<3x2xf64>
  toy.print %5 : tensor<3x2xf64>
```

Every `tensor<*xf64>` is now ranked. The pass walks operations whose operands
are known and asks each one to set its own result type through the
`ShapeInference` interface, so `transpose` of a `2x3` reports `3x2` and `mul`
reports its operand shape. This is the first of the two boundaries worth
dwelling on in a talk, because it is the step that makes everything after it
possible: the lowering needs literal loop bounds, and they come from here.

It also only works because inlining ran first. A generic function whose
parameters are unranked has no shape to infer until a call site's concrete types
are substituted for them.

### Banners 7 and 8: what shape inference unlocked

Banner 7, canonicalize. The two casts are now `2x3` to `2x3`, identities, and
they fold away. The transposes read `%0` directly.

Banner 8, CSE. The two transposes are identical operations on the same operand,
so one survives:

```mlir
  %1 = toy.transpose(%0 : tensor<2x3xf64>) to tensor<3x2xf64>
  %2 = toy.mul %1, %1 : tensor<3x2xf64>
```

`docs/examples/dumps/codegen.pass-statistics.txt` records this as `1 num-cse'd`
under the `toy.func` pipeline. `toy.mul %1, %1` multiplies a value by itself,
which is what the source said: `transpose(b) * transpose(a)` where `a` and `b`
are the same constant.

### Banner 9: partial conversion

This boundary is worth the most time in a talk: it shows partial conversion,
bufferization and the dialect mix on one screen. Three things happen at once.

Operations change. The constant becomes six stores, and each Toy operation
becomes a loop nest:

```mlir
    affine.for %arg0 = 0 to 3 {
      affine.for %arg1 = 0 to 2 {
        %0 = affine.load %alloc_1[%arg1, %arg0] : memref<2x3xf64>
        affine.store %0, %alloc_0[%arg0, %arg1] : memref<3x2xf64>
      }
    }
```

That is the transpose, done by reading `[j, i]` while writing `[i, j]`. No
operation copies data in transposed order.

Types change. `tensor<3x2xf64>` becomes `memref<3x2xf64>`, and the pass
allocates three buffers, each with a deallocation before the terminator. The
values became addresses, which is where the data-flow graph stops describing the
contents.

And one operation deliberately does not change:

```mlir
    toy.print %alloc : memref<3x2xf64>
```

`toy.print` is still here, in a function otherwise made of `affine`, `arith`,
`memref` and `func` operations. It survives because the conversion target marks
it dynamically legal, legal exactly when its operand is no longer a tensor, so
the framework rewrites the operand and leaves the operation standing. The
mechanism is in [08. Lowering to affine](08-lowering-to-affine.md); this dump is
the evidence that it worked.

`toy.func` and `toy.return` became `func.func` and `return` at the same time,
which is why the four passes after this one are anchored on `func.func`.

CSE merged the two transposes at banner 8, yet the multiply nest here loads
twice from the same place:

```mlir
        %0 = affine.load %alloc_0[%arg0, %arg1] : memref<3x2xf64>
        %1 = affine.load %alloc_0[%arg0, %arg1] : memref<3x2xf64>
        %2 = arith.mulf %0, %1 : f64
```

The pattern for a binary operation emits one load per operand, and both operands
are the same value. Lowering introduced a redundancy that the level above had
already removed, which is why CSE runs again at this level.

### Banners 10 and 11: cleaning up at the new level

Banner 10, canonicalize on `func.func`. The index constants disappear and the
stores take literal indices, `affine.store %cst_4, %alloc_6[0, 0]` where banner
9 had `[%c0, %c0]`. The floating-point constants are hoisted to the top of the
block. Loop and buffer counts are unchanged.

Banner 11, CSE. The duplicate load from banner 9 collapses, giving `arith.mulf
%0, %0`. The statistics file records a second `1 num-cse'd`, this time under the
`func.func` pipeline. Two CSE passes, one per abstraction level, each removing
one operation, because each level created its own redundancy.

### Banners 12 and 13: what -opt adds

Banner 12, `AffineLoopFusion`. The two nests become one, with the transpose's
store and the multiply's load in the same body. Four `affine.for` become two.
The three allocations are all still here.

Banner 13, `AffineScalarReplacement`. The intermediate `3x2` buffer disappears:
the value stored by the transpose is forwarded directly to the load that
consumed it, so the buffer holding it has no remaining reader.

```mlir
    affine.for %arg0 = 0 to 3 {
      affine.for %arg1 = 0 to 2 {
        %0 = affine.load %alloc_5[%arg1, %arg0] : memref<2x3xf64>
        %1 = arith.mulf %0, %0 : f64
        affine.store %1, %alloc[%arg0, %arg1] : memref<3x2xf64>
      }
    }
```

Worth being precise about which pass did what, because it is easy to credit both
effects to fusion. Fusion merged the loops and left three buffers. Scalar
replacement removed the buffer and left two loops. The end-to-end effect on loop
count is visible without reading the trace at all:

```console
$ grep -c 'affine.for' docs/examples/dumps/codegen.mlir-affine.txt docs/examples/dumps/codegen.mlir-affine.opt.txt
docs/examples/dumps/codegen.mlir-affine.txt:4
docs/examples/dumps/codegen.mlir-affine.opt.txt:2
```

## What the levels below add

The trace stops at the affine level because that is where `-emit=mlir-affine`
stops. The dumps continue, and the two worth showing are short.

`codegen.mlir-llvm.txt` is the same program with nothing but the LLVM dialect
left. The memref that was one value becomes a five-field descriptor,
`struct<(ptr, ptr, i64, array<2 x i64>, array<2 x i64>)>`: allocated pointer,
aligned pointer, offset, sizes, strides. `toy.print`, the operation that
survived banner 9, finally becomes a loop calling `printf`. [09. Lowering to
LLVM](09-lowering-to-llvm.md) has the details.

`codegen.llvm.txt` and `codegen.llvm.opt.txt` are LLVM IR before and after
LLVM's own optimizer, and the difference is the most quotable number in the set:
186 lines with 18 branches and 2 `printf` calls become 44 lines with no branches
at all, 6 `printf` calls and 4 `putchar` calls. The loops are gone because every
value was known at compile time. What the program prints is in
`codegen.jit.txt`, and `codegen.object-symbols.txt` shows the same program as a
real object file.

## Regenerating and caveats

    docs/examples/dump-examples.sh            # rewrite every dump
    docs/examples/dump-examples.sh --check    # what the dumps test runs

Three caveats before presenting from this.

The Toy levels are stable across LLVM versions; `mlir-llvm` and `llvm` are not,
since they embed LLVM's own spelling of its dialect and the numbering of its
debug metadata. A version bump will move those dumps.

The claim that banners 1 to 3 belong to the inliner's own pipeline is read from
the dump's contents and from the pipeline string, where `inline` carries
`default-pipeline=canonicalize`. Why it runs three times for two functions, once
per function and once more on `main` after inlining, is consistent with what the
banners show but is not something this trace proves on its own.

The order of the hoisted floating-point constants at banner 10 is an artifact of
how the canonicalizer moved them, not something the source or the pipeline
specifies. It is not worth explaining on a slide.
