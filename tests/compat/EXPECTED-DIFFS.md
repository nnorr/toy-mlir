# Expected differences from the upstream tutorial

`toyc-ch7` is this repo's golden reference. `compare-upstream.sh` sweeps a
randomized corpus through both compilers at every stage and treats any
difference as a failure unless it is listed here.

The claim being tested is narrow on purpose:

> For a **valid** Toy program, this repo's `toyc` produces byte-identical output
> to `toyc-ch7` at every stage, with and without `-opt`, except for binary
> operator **column numbers** (deviation D2), which show directly in `-emit=ast`
> and indirectly in `-emit=llvm` debug metadata.
>
> Two error paths differ deliberately and are exempted by name: D8 below, and the
> parser/lexer/MLIRGen diagnostics D1, D3 and D4, which are checked as fixtures
> rather than swept.

Everything below is measured against `toyc-ch7` from the LLVM 24.0.0 build in
`~/dev/08_mlir_toy/build`, not quoted from the tutorial text.

## The sweep

| | |
| --- | --- |
| Corpus | `reference/tests/**/*.toy` (the tutorial's own programs) plus N generated by `gen-programs.py` |
| Stages | `-emit=ast`, `mlir`, `mlir-affine`, `mlir-llvm`, `llvm`, `jit` |
| Settings | with and without `-opt` |
| Streams | stdout and stderr merged; for `-emit=jit`, stdout compared on its own as well |
| Normalization | the input path, and the compiler's own name where it prefixes a diagnostic — `argv[0]` is necessarily `toyc` for us and `toyc-ch7` upstream, matched only at the start of a line followed by `": "`. No value, type, symbol, SSA number or diagnostic text is rewritten. |

A program **upstream itself** cannot compile is still compared. Reproducing an
upstream failure faithfully is an equivalence result, not a reason to look away,
and nothing is skipped: the summary prints `NOT COMPARED: 0`.

`reference/tests/**/scalar.toy` is the interesting case. It reshapes a rank-0
tensor to `2x2`, which trips an assertion inside MLIR itself:

```
PROG: .../mlir/lib/IR/BuiltinAttributes.cpp:1118: DenseElementsAttr
mlir::DenseElementsAttr::reshape(ShapedType): Assertion
`newType.getNumElements() == curType.getNumElements() &&
"expected the same number of elements"' failed.
```

Both compilers abort there, at the same file and line, with the same text and the
same exit code 134, at all nine stage/opt combinations that reach it. Once
`argv[0]` is normalized the outputs are identical, so these count as passes —
54 of them.

## D2 — binary operator locations (the only permitted difference)

A `BinaryExprAST` carries the operator's location. Upstream reads the location
*after* consuming the operator token, so it records where the right-hand side
starts.

Measured, on `return a + b;` with `+` at column 12 and `b` at column 14:

```
upstream:  BinOp: + @INPUT:17:14
ours:      BinOp: + @INPUT:17:12
```

Where it shows and where it does not, as measured by the sweep:

* `-emit=ast` — visible, directly, in `BinOp:` lines.
* `-emit=mlir`, `-emit=mlir-affine`, `-emit=jit` — **not** visible. MLIR does not
  print locations unless asked, so these stages must be byte-identical.
  (`-mlir-print-debuginfo` by hand shows the shift in the `loc(...)` of
  `toy.add`/`toy.mul`.)
* `-emit=llvm` — **visible, indirectly**, and this is worth understanding
  because it looks alarming. Upstream's binop location equals its right-hand
  side's location, so the two share one `!DILocation` and LLVM emits a single
  metadata node. With the operator's own column they are distinct, so one extra
  node appears — and every `!dbg` reference after it renumbers. A
  two-column difference therefore produces a diff hundreds of lines long, in
  which the instruction stream is nevertheless identical.

Measured on `reference/tests/Ch2/codegen.toy`:

```
180c180
< !10 = !DILocation(line: 5, column: 25, scope: !11, inlinedAt: !12)
---
> !10 = !DILocation(line: 5, column: 23, scope: !11, inlinedAt: !12)
```

and on a generated program with several binary operations, a 525-line diff that
collapses to a single extra `!DILocation` once metadata numbering is normalized.

`compare-upstream.sh` accepts exactly this much and no more:

* at `-emit=ast`, it masks the column in `BinOp:` lines and requires everything
  else to match;
* at `-emit=llvm` and `-emit=mlir-llvm`, it normalizes debug-metadata numbering
  and masks `column:` in `!DILocation`, then requires (a) the instruction stream
  to match **exactly** and (b) the set of distinct `!DILocation` nodes to match.
  A changed line number, a changed scope, or any instruction difference fails.

Such comparisons are reported as `D2-only` rather than as passes, so the number
of affected programs is always on screen.

## D8 — `-emit=jit` with no `main` (the second permitted difference)

The only genuine behavioral difference the sweep finds outside D2, and it is an
error path that a valid program never reaches. It shows on
`reference/tests/**/empty.toy`, an empty source file, at `-emit=jit`.

Upstream tests the `llvm::Error` returned by `invokePacked()` but never consumes
it, so the `Error` destructor kills the process:

```
$ toyc-ch7 empty.toy -emit=jit
JIT invocation failed
Program aborted due to an unhandled Error:
Symbols not found: [ _mlir_main ]
exit 134
```

Ours reports the same cause and exits normally:

```
$ toyc empty.toy -emit=jit
JIT invocation failed: Symbols not found: [ _mlir_main ]
exit 255
```

`compare-upstream.sh` admits this only when all of the following hold, so no
other JIT difference can hide behind it: upstream exited 134 having printed both
`JIT invocation failed` and `Program aborted due to an unhandled Error`; we
exited nonzero without aborting; and the `Symbols not found: [...]` payload is
character-for-character the same on both sides. Reported as `D8-only`.

  opt settings:  none, -opt

Every comparison is accounted for: 2324 byte-identical, 542 attributable to D2

## Error paths: D1, D3, D4

These are **not** part of the valid-program sweep — a valid program never
reaches them. They live in `fixtures/` and their diffs are recorded in
`expected/`, so a change in our diagnostics is caught rather than silently
accepted.

Recorded with:

```
tests/compat/compare-upstream.sh --fixtures-only --update
```

The recorded diffs are in `expected/`, and the `compat_fixtures` ctest entry
checks each fixture against the one recorded for it. A diff that changes shape
fails that test until someone re-runs the command above, which is how the
doubled `error: error:` prefix in the D4 message was caught after it was fixed.

### D1 — malformed numbers (`fixtures/malformed-number.toy`)

Upstream lexes `1.23.45` as a single token, hands the text to `strtod`, keeps the
`1.23` that parsed and discards the rest silently.

Measured upstream behavior:

```
$ toyc-ch7 malformed-number.toy -emit=ast
...
  VarDecl a<> @INPUT:5:3
    1.230000e+00 @INPUT:5:11
exit 0
```

Ours reports it at `5:11` and refuses to continue (nonzero exit). `hadError()`
on the lexer is what the driver consults.

### D3 — missing initializer (`fixtures/missing-initializer.toy`)

Upstream accepts `var a = ;`. The parse "succeeds", the `VarDeclExprAST` holds a
null initializer, and `-emit=ast` prints a childless `VarDecl` and exits 0:

```
$ toyc-ch7 missing-initializer.toy -emit=ast
...
  VarDecl a<> @INPUT:5:3
  Print [ @INPUT:6:3
exit 0
```

The error only surfaces two stages later:

```
$ toyc-ch7 missing-initializer.toy -emit=mlir
loc("INPUT":5:3): error: missing initializer in variable declaration
exit 1
```

and `toyc-ch1`'s dumper does not survive it at all — it `dyn_cast`s the null
pointer and aborts:

```
$ toyc-ch1 missing-initializer.toy -emit=ast
Assertion `detail::isPresent(Val) && "dyn_cast on a non-existent value"' failed.
exit 134
```

Ours reports a parse error at the point of failure instead.

### D4 — redeclaration (`fixtures/redeclaration.toy`)

Upstream's `MLIRGen::declare` returns failure without emitting anything, so the
compile fails with **no diagnostic whatsoever**:

```
$ toyc-ch7 redeclaration.toy -emit=mlir
exit 1
```

Ours emits an error naming the variable, located at the second declaration.

## Differences that are *not* expected

Worth stating, because the sweep enforces it: nothing else may differ. In
particular the following must be byte-identical, and a diff in any of them is a
bug in this repo rather than a documented deviation:

* SSA value numbering and the order operations are emitted in;
* attribute and type syntax, including `dense<...>` formatting and
  `!toy.struct<...>`;
* which functions are `private`, and which survive inlining;
* the affine loop structure, and what `-opt` fuses or eliminates;
* the memref descriptor's five fields in the LLVM dialect and in LLVM IR;
* the printed values from `-emit=jit`;
* exit codes on every path, including the error paths above.
